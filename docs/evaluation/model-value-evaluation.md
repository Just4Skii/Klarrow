# Model-Value Evaluation: Deterministic Parsing vs Optional Local Llama Extraction

Run: `eval-dev-20261019-final` (consolidated)
Artifacts: `results/evaluation/model-value-evaluation.json`, `results/evaluation/model-value-evaluation.csv`, `results/evaluation/runs/eval-dev-20261019-final/`
Runner: `scripts/evaluation/run-scenario.mjs`
Date: 2026-10-19

## Purpose

Measure what the optional local-Llama extraction step adds, and what it costs, relative to the
deterministic parser alone, across the three authored evaluation scenarios. This supports the
submission claim that the deterministic core works standalone and that AI extraction is an
optional, human-supervised sidecar. All expectations were authored by hand from the document text
and locked in `ground-truth.json` per scenario before execution; document manifests are
SHA-256-verified by the runner before every run.

## Environment and method

- Deterministic mode: `EXTRACTION_MODE=deterministic_only`, `LLAMA_EXTRACTION_DISABLED=true`.
- Llama mode: Ollama at `http://127.0.0.1:11434/v1`, model `llama3.2:3b`, `temperature=0`,
  `LLAMA_TIMEOUT_SECONDS=180`. Requests are live; nothing is cached.
- Each run starts a fresh API instance with an isolated data root, uploads the scenario documents,
  runs extraction, generates candidate relationship links, computes matches and gap findings, applies
  the same scripted human decisions (link confirmations, one alias confirmation with regeneration in
  scenario C), then re-computes findings and trace snapshots, and finally checks audit/home output.
- Verdicts are computed by 13 boolean checks against the locked ground truth:
  1. required links all present, 2. no unexpected links, 3. expected noise links match with expected
  state, 4. no forbidden link patterns, 5. verbatim-copy traps all preserved verbatim, 6. llama runs
  must create at least one AI-extraction fact row, 7. deterministic runs must create zero AI rows,
  8. expected match proposals found with expected state, 9. no forbidden match pairs, 10. expected
  findings present pre-review, 11. expected findings present post-decisions, 12. forbidden findings
  absent, 13. all trace snapshots match expected confirmed scope, possible scope, state counts and
  mass-balance status/figures.
- Claim recall measures whether authored expected claims (identifier plus quantity/unit) appear in
  extracted fact rows; it is reported as a metric, not a pass/fail check.

## Observations

- Scenario A (baseline replication): both modes reproduce the expected pipeline, including the
  near-match proposal for the confusable lot pair (proposal direction `LeftValue=RM-O873`,
  `RightValue=RM-0873`, consistent with the recorded Run 4 artefacts). Llama mode additionally
  surfaces 15 prose-derived candidate rows and matches all 6 authored claims.
- Scenario B (forward trace): both modes complete all integrity checks. Llama mode misses two
  authored claims (the two dispatch-note quantities, `DSP-6202 1500units`, `DSP-6201 900units`),
  giving 0.60 claim recall, but the facts it does produce are grounded (token, quantity and
  locator recall all 1.00) and all relationship, finding and trace checks pass.
- Scenario C (fragmented evidence): deterministic mode stays clean. Llama mode introduces three
  extra candidate links: two AI-extraction `raw_to_batch` candidates crossing the variant codes
  into the unrelated second batch (`RM-77O2 -> PB-2026-1206-D`, `RM-7702 -> PB-2026-1206-D`) and
  one `supplier_delivery` candidate for `Sunland Cocoa Trading (Pvt) Ltd -> RM-77O2` generated by
  the deterministic relationship step from an AI-extracted fact. All three remain `Candidate`
  state; nothing is auto-confirmed. The extra candidates then shift the pre-review possible scope
  and the post-alias trace state counts, which is what breaks the two failing checks. Claim recall
  is 0.25 (only `RM-7702 320kg` was matched; the three variant-code quantity claims were missed).
- In all llama runs, every fact that was extracted carried a locator (locator rate 1.00), and no
  forbidden pattern or verbatim-copy violation occurred. The differences are about extra
  candidates and missed claims, not about fabricated identifiers entering confirmed state.

## Provider hardening disclosure (pre-report runs)

The first llama-suite execution (`eval-dev-20261019-llama-1`) exposed a robustness issue: scenario
B's extraction run failed with `Fact rawValue must be a string.` because the model returned at least
one fact row with a non-string `rawValue` (e.g. a bare number), and the provider treated any
malformed row as a whole-response failure, aborting the run with zero AI facts. A single-scenario
retry (`eval-dev-20261019-llama-2`) reproduced the same failure exactly.

As a result, the provider parser was hardened (`LlamaProvider.TryParse`): non-object rows are
skipped, rows without a usable `rawValue` are skipped, and numeric/boolean `rawValue` values are
coerced to their literal text. Per-fact grounding, review and confirmation rules are unchanged;
malformed rows can no longer disqualify an otherwise valid response, and rows still flow through
the same quote-grounding and human-review pipeline. A regression test was added
(`Provider_adapter_skips_malformed_fact_rows_and_coerces_numeric_raw_values`), and the full test
suite passes 43/43. The results in this report were produced after that change, with run
`eval-dev-20261019-final` consolidating deterministic (`eval-dev-20261019-f`) and llama
(`eval-dev-20261019-llama-3`) executions on the same binary. The pre-fix run identifiers above are
retained so the history is auditable.

## Limitations

- One small local model (`llama3.2:3b`) via Ollama; results will differ with other models or
  providers. `temperature=0` reduces but does not fully eliminate sampling variance on some
  backends.
- All documents are authored synthetic evidence; the scenarios exercise specific mechanics
  (confusable identifiers, fragmented chains, credit-return traps) and are not a statistical
  sample of real-world paperwork.
- Claim recall depends on the authored expected-claim list and on the scripted decision procedure;
  it is not a measure of real-world extraction accuracy.
- This evaluation does not measure latency, cost, or throughput; it measures integrity behaviour
  and coverage on the three scenarios only.

## Conclusion

Across these three scenarios the deterministic parser alone met every locked expectation
(3/3 scenarios, 13/13 checks each). The optional Llama extraction added prose-derived candidate
rows (10-15 per scenario) with complete token, quantity and locator grounding, fully passed A and
B, and on the fragmented-evidence scenario C added three extra `Candidate` links that lowered the
verdict to 11/13 while never auto-confirming anything. No AI-extracted content enters confirmed
state without human review in any run. These results support positioning deterministic parsing as
the reliability baseline for structured documents and Llama extraction as an optional, supervised
assist that increases candidate coverage at the cost of reviewer effort on fragmented evidence.
